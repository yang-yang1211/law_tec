# 法訊雷達團隊開工通知

以下內容可貼到團隊群組；請視需要補上日期。

---

大家好，法訊雷達的分工、開工步驟和防呆規則已整理在[團隊分工與 GitHub 協作](https://github.com/yang-yang1211/law_tec/blob/docs/team-workplan-kickoff/docs/%E5%9C%98%E9%9A%8A%E5%88%86%E5%B7%A5%E8%88%87GitHub%E5%8D%94%E4%BD%9C.md)。請先讀自己的段落，再到負責的 GitHub Issue 留言認領，寫明預計交付日、第一個交付物和需要的協助。

**第一階段目標：** 做出「選關注 → 看個人化法訊 → 查官方來源 → 問答附引用 → LINE 更新通知」的一條可重現流程。法律資料要可回查；LINE 先以指定測試帳號驗證，尚未連接的部分要明確標成模擬。

| 成員 | 先做的事與負責範圍 | 驗收情境 | Issue |
|---|---|---|---|
| A（我） | 定使用情境與共用資料規格、整合端到端 Demo、主責 Pitch 和提交檢查 | 至少 2 個端到端情境 | [#1](https://github.com/yang-yang1211/law_tec/issues/1)、[#7](https://github.com/yang-yang1211/law_tec/issues/7)、[#9](https://github.com/yang-yang1211/law_tec/issues/9)、[#10](https://github.com/yang-yang1211/law_tec/issues/10) |
| B | 做個人化 feed、三種檢視、排序規則和推薦理由 | 至少 2 個首頁情境 | [#2](https://github.com/yang-yang1211/law_tec/issues/2) |
| C | 整理至少 6 筆官方核對資料，完成引用問答與資料不足拒答；C 對資料正確性負責 | 至少 2 個資料／問答情境；E 抽查 2 筆來源 | [#3](https://github.com/yang-yang1211/law_tec/issues/3)、[#4](https://github.com/yang-yang1211/law_tec/issues/4) |
| D | 實作 LINE 帳號連結、Webhook 簽章驗證與事件去重，再依使用者偏好對指定測試帳號呼叫 Push API | 至少 3 組 API 情境；實際推播前確認帳號與訊息 | [#5](https://github.com/yang-yang1211/law_tec/issues/5)、[#6](https://github.com/yang-yang1211/law_tec/issues/6) |
| E | 維護驗收總表和缺陷追蹤，抽查高風險項目，整理乾淨瀏覽器下的 Demo 步驟 | 至少 1 個乾淨狀態 Demo 情境；重驗跨模組問題 | [#8](https://github.com/yang-yang1211/law_tec/issues/8)，協助 #3、#7、#9、#10 |

**驗收至少 10 個情境由全員分攤：** A 2、B 2、C 2、D 3、E 1。每位功能主責先跑自己的情境並把步驟、預期、實際結果留在 Issue；E 彙整總表和抽查，不需要代替大家設計、執行全部項目。

**今天請先完成：**

1. 每人到負責的 Issue 留言認領，寫預計交付日、第一個交付物和依賴事項。
2. A 在 #1 確認使用情境和共用欄位後，通知 B、C、D 依同一格式開始；E 先建立驗收總表。
3. D 在 #5 先確認測試 LINE Official Account、channel、單一測試帳號和 Webhook 測試環境；缺少時立即在 Issue 記錄阻塞，先做模擬但不可宣稱已連上 API。
4. 每天在自己的 Issue 更新完成事項、下一步、阻塞和驗收狀態；跨模組欄位或規則變更先通知 A 和受影響的成員。

**共同防呆：** 未核對的資料不進入回答或通知；法律狀態不確定時不推測。LINE 不做群發，未同意、已停用、已解除連結或重複事件不發送。API 憑證不得放進前端、截圖、Issue 或 Git。PR 走獨立分支和 Review，不直接推 main。

正式繳件內容與日期依專案簡章及主辦單位公告為準。
