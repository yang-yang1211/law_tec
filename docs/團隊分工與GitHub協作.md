# 團隊分工與 GitHub 協作

> 團隊以 A–E 作為成員代號，A 是你。這份文件說明每位成員從哪裡開始、要交付什麼、如何驗收，以及遇到規格或資料問題時怎麼處理。GitHub Issue 是任務進度的唯一記錄位置。

## 目標流程

第一版先完成一段可重現的展示：**選擇關注 → 看到個人化法訊 → 查看官方來源 → 詢問並看到引用 → 收到符合偏好的 LINE 更新**。網頁目前是原型。LINE 先做受控的測試帳號串接；若測試環境尚未到位，先用模擬流程開發，但不可把模擬說成已連上 LINE API。示意法律資料也不可說成真實法律進度。

## 一眼看懂先後順序

- **A：** 先完成 #1，定使用情境、共用欄位和模組邊界；負責整合、Pitch 和提交檢查。
- **B：** 依 #1 的欄位做 #2；先用共用示例資料，不另造一套格式。
- **C：** 先做 #3 核對資料，再用同一批資料完成 #4 引用問答與拒答。
- **D：** 完成 #5 LINE 帳號連結和 Webhook 串接，再以 #6 依偏好呼叫 Push API；先用受控測試帳號。
- **E：** 負責 #8 驗收清單、缺陷追蹤和重測；各模組主責提供並先跑自己的情境，E 不必從零設計或執行全部測項。
- **整合：** B、C、D 各有可展示切片後，由 A 做 #7；A 負責 #9、#10，E 協助截圖、少量抽查和重測。

## 五位成員的開工清單

### A｜使用情境、規格、整合與競賽交付

**負責 Issue：** #1、#7、#9、#10

**第一步怎麼做：**

1. 在 #1 寫清楚主要使用者情境、首版範圍和 Demo 成功條件。
2. 定義共用 NewsItem 的欄位、型別、允許值、日期時區和未知值表示方式；請 B、C、D、E 確認各自需要的欄位。
3. 指定共用示例資料的位置和版本。欄位要增加或改名時，先更新 #1、說明影響，再通知所有受影響的成員。
4. 在 #7 排整合節點，用同一筆資料串接首頁、來源問答和通知；整合問題記錄回對應 Issue，不在 A 的電腦上留一套特殊設定。
5. A 主責 #9 的兩分鐘故事線和 Demo 腳本；把 B、C、D 的功能和限制收進同一份簡報。A 主責 #10，依簡章列出文件、連結、影片、格式和截止時間；E 協助檢查素材可開啟。

**交付物：** 使用情境和資料規格、決策及阻塞紀錄、端到端 Demo、Pitch／Demo 腳本、提交檢查清單。

**完成條件：** B、C、D 確認共用欄位；整條流程可依腳本重跑；未決事項有負責人和期限；提交項目逐項對照簡章。

**A 也負責驗收情境：** 撰寫並執行至少 2 個端到端情境，例如「關注租屋→看到推薦→查看來源→問答」和「符合條件的核對更新→通知測試帳號」。

### B｜個人化首頁與推薦

**負責 Issue：** #2

**開始前先看：** #1 的共用欄位、現有網頁原型和 C 的示例資料。規格未定時，先在 #1 提出缺項，不自行另造欄位。

**工作步驟：**

1. 列出卡片要呈現的標題、摘要、狀態、標籤、時間、來源和推薦原因。
2. 在 #2 寫明標籤匹配、最新排序欄位、同分時的排序方式和推薦理由，再依這套規則實作。
3. 讓「為你推薦／我追蹤的／最新消息」讀取共用示例資料；補上搜尋、空結果和缺少可選欄位時的畫面。
4. 附主要畫面截圖、手動步驟和結果，交給 A 整合、E 登記驗收。

**完成條件：** 三種檢視各自符合規則；每則推薦都有理由；追蹤與最新結果可解釋；不自行補造法律狀態或來源。

**B 負責驗收情境：** 至少 2 個首頁情境，例如「匹配標籤的項目排前面」和「無匹配／搜尋無結果時顯示正確空狀態」。B 自己先跑並記錄結果。

### C｜官方資料、法案狀態與引用問答

**負責 Issue：** #3、#4；E 抽查來源。

**開始前先看：** #1 的 NewsItem 規格和計畫書列出的官方來源；先確認資料集欄位和日期，再整理內容。

**工作步驟：**

1. 在 #3 記錄官方資料來源、資料集名稱、網址、可用欄位和查核日期。
2. 整理至少 6 筆示例 NewsItem；每筆保留原始來源、日期、狀態和標籤。
3. 分清提案、審議、通過、公布和施行；標題不能當狀態依據。遇到來源衝突、缺漏或日期不明，標記待確認，先排除於問答與通知。
4. 和 E 抽查至少 2 筆資料；在 #3 記下更正依據。C 仍是所有資料正確性的主責，不把整批核對工作交給 E。
5. 在 #4 用同一批核對資料準備可回答問題和必須拒答的問題；回答附來源名稱、網址、資料日期和狀態。

**完成條件：** 法律事實可回查官方來源；引用和回答相符；資料不足時說明無法確認、不自行推測；抽查發現的高風險問題已處理。

**C 負責驗收情境：** 至少 2 個情境，例如「來源支持的答案附對應引用」和「來源不足或來源衝突時拒答」。C 自己先跑並記錄結果。

### D｜LINE 帳號連結、Webhook 與通知 API

**負責 Issue：** #5、#6；A 協助確認測試帳號和應用端登入方式，C 提供核對資料。

**工作範圍：** D 不只做介面示意。目標是在受控測試環境完成一條可驗證的實際串接：LINE 帳號連結成功後，依使用者同意與關注標籤，將一筆核對過的重要更新 Push 到指定測試帳號。

**開始前先確認：**

1. 和 A 確認測試用 LINE Official Account、Messaging API channel、受控測試帳號、Webhook 可接收的測試環境及憑證管理方式。
2. 確認網站端如何辨認測試使用者。現有原型沒有正式登入系統；若只做展示用登入／session，必須標明是測試機制，不能說成正式帳號安全方案。
3. 憑證不可放進前端、Issue、截圖或 Git；只存在伺服器環境設定。若測試環境尚未取得，先在 #5 記錄阻塞，先完成模擬接收器和操作流程，不宣稱 API 串接完成。

**工作步驟：**

1. **帳號連結：** 使用者先加入並啟動官方帳號；伺服器取得 LINE user ID 後向 Messaging API 申請一次性 link token，提供連結 URL。網站登入後產生不可預測、一次性 nonce，完成 LINE account-link 流程；收到成功的 accountLink Webhook 後才建立帳號對應。失敗、過期、重複使用和解除連結都要有明確結果。
2. **Webhook 安全：** 建立 Webhook endpoint；使用官方 SDK 或正確的簽章驗證方式，先以未解析的原始 request body 驗證 x-line-signature，驗證失敗就不處理事件。
3. **事件處理：** 處理帳號連結成功／失敗事件；用 webhookEventId 去重，並考慮事件重送或時間順序不同，避免重複建立連結或重複推播。
4. **通知 Push：** 從 C 的核對資料建立通知候選，依已同意、尚未解除連結、通知仍開啟、標籤匹配和重要程度決定是否呼叫 Push API。先只送單一指定測試帳號，不做群發；通知內含摘要、狀態、更新時間和來源連結。
5. **失敗處理：** 留下不含 token、個資或完整訊息內容的必要紀錄；處理無效／過期連結、簽章錯誤、停用通知、重複事件和 API 失敗。重試前先確保不會重複推送。

**交付物：** 可重現的測試帳號連結流程、Webhook endpoint 和簽章驗證、帳號連結與解除連結、通知偏好匹配、單一測試帳號 Push、失敗情境紀錄；若環境未到位，另附模擬流程和阻塞證據。

**完成條件：** 成功連結後能建立正確帳號對應；錯誤簽章不處理；同一 webhookEventId 不重複推播；未同意、停用、解除連結或不符合條件時不送；符合條件時只通知指定測試帳號；API 未實測的部分清楚標示為模擬。

**D 負責驗收情境：** 至少 3 組情境，覆蓋成功連結／解除、失敗或無效連結、簽章錯誤或 webhook 重送、符合條件 Push 與停用／不匹配不送。每次實際 Push 前確認測試對象和訊息內容。

### E｜驗收協調、抽查與缺陷追蹤

**負責 Issue：** #8；不再獨自撰寫全部測項或承擔全份 Pitch／提交檢查。

**工作步驟：**

1. 從 #1 的使用情境建立 #8 驗收表格欄位：情境、負責人、步驟、預期、實際、結果、問題連結。
2. 請 A、B、C、D 各自提供並執行自己的情境；至少累計 10 個情境。E 負責彙整、檢查是否有重複或漏掉關鍵流程，不代替功能主責跑完所有測項。
3. E 自己設計並執行至少 1 個「乾淨瀏覽器狀態」Demo 情境，並抽查 C 的 2 筆來源和 D 的高風險通知情境。
4. 發現問題時開 Issue 或連回原 Issue，寫重現步驟、預期與實際結果、證據、嚴重程度和主責。修正後由原功能主責重跑；E 只重驗高風險與跨模組問題。
5. 協助 A 收集截圖、操作素材和問題摘要；Pitch、Demo 主線、簡章對照及提交清單由 A 負責定稿。

**完成條件：** 至少 10 個情境由對應主責執行並留結果；E 已整理問題和風險；高風險／跨模組修正有重驗紀錄；Demo 可從乾淨狀態重跑。

## 團隊工作流程

### 1. 開工與規格確認

1. 每人到負責的 Issue 留言認領，列出預計交付日、協作者和需要的協助。
2. A 在 #1 定稿情境與共用欄位；B、C、D 回覆確認，E 補充驗收表欄位。
3. A 留下「第一版規格已確認」及版本日期後，B、C、D 依規格開始；E 可先建立驗收總表。
4. D 在 #5 的第一個進度更新就確認測試 channel、測試帳號和 webhook 環境；未取得時由 A 記錄阻塞和備援決策。

### 2. 平行開發與交付

1. 每個 Issue 開獨立分支，例如 feat/issue-2-feed；一次只混一個 Issue 的改動。
2. B、C、D 先交最小可展示切片；C 的核對資料交付後，D 才能以其內容測通知。
3. 每位主責先跑並記錄自己負責的手動情境，PR 連回 Issue，附摘要、步驟、結果、來源和必要截圖。
4. 欄位變更、來源疑義、真實 API 測試條件等跨模組事項，先在 Issue 留紀錄並通知 A，不以私訊口頭結論代替。

### 3. Review、整合與重驗

1. 每個 PR 至少一位非主責成員 Review；共用欄位或跨模組變動由 A 確認。驗收條件未通過時先修正，不合併。
2. A 依 #7 串接同一筆資料；E 更新驗收總表，負責人各自執行自己的情境。
3. 修正後由原主責重跑失敗項目；E 抽查高風險／跨模組項目並記錄結果。
4. A 依整合結果定稿 Pitch 和提交清單；E 協助確認素材與連結能開啟。

### 4. 每日同步格式

在負責的 Issue 留短更新，不只在聊天群組報進度：

- 昨天完成：
- 今天要完成：
- 卡住／需要誰協助：
- 分支／PR／交付物連結：
- 驗收情境和結果：

## 防止意外的停止條件

遇到以下情況先暫停相關功能，記錄在 Issue 並通知 A 和受影響的主責：

- **規格不一致：** 欄位或狀態名稱對不上時，不在單一模組自行轉換；先更新 #1，讓所有使用者同步。
- **來源不明或相互矛盾：** 標記待確認，不進入問答、首頁事實敘述或通知；由 C 查核，E 抽查。
- **法律狀態不確定：** 不把提案寫成現行規定；不能確認生效日就標示未知並停止推論。
- **LINE 可能誤發：** 未同意、已停用、已解除連結、非核對資料或重複事件一律不發；實際 API 測試只送指定測試帳號，不做群發。
- **Webhook 簽章錯誤：** 不處理事件；先查原始 request body、channel secret 和驗證方式，不可略過驗證來讓 Demo 通過。
- **機密或個資可能入庫：** 不貼到 Issue、PR、截圖或 Git；若憑證曾外洩，立即通知 A 並撤換，不只刪除文字。
- **Git 衝突或意外大範圍改動：** 不對 main 直接提交，不強制推送或重設來掩蓋問題；先保留現況、記錄錯誤訊息並找 A 協助。
- **Demo 狀態殘留：** 展示前用乾淨瀏覽器確認關注標籤、收藏和連結狀態；示意內容清楚標明為示意。

## 分支與安全規則

- main 保持可展示；每個 Issue 使用獨立分支，透過 PR 合併回 main，不直接推送 main。
- 分支名稱建議 feat/issue-編號-短名稱；PR 標題含 Issue 編號，內文使用 Closes #編號。
- PR 不混入其他 Issue 改動；需求變更另開 Issue 或更新原 Issue，並說明影響範圍。
- API 金鑰、LINE token／secret、密碼和真實個資不得提交；伺服器憑證只放本機或受控環境變數，不放前端。
- 真實 LINE 推播前先確認使用者同意、指定測試帳號、通知條件和停止方式；無法確認時維持模擬。

## LINE 官方技術參考

- [LINE 帳號連結](https://developers.line.biz/en/docs/messaging-api/linking-accounts/)：link token、nonce、accountLink 事件和解除連結。
- [Webhook 簽章驗證](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature)：使用 channel secret 驗證 x-line-signature；驗證前不可解析或改寫原始 body。
- [接收訊息與 Webhook 重送](https://developers.line.biz/en/docs/messaging-api/receiving-messages)：使用 webhookEventId 辨識重複事件，並注意重送後事件順序可能不同。
- [傳送訊息](https://developers.line.biz/en/docs/messaging-api/sending-messages/)：Push API 和訊息傳送方式。
