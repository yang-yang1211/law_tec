跨模組先使用以下欄位名稱；要新增欄位時先在此 Issue／文件提出，避免各自使用不同名稱。

## 建議 GitHub 看板

使用一個 GitHub Project 看板，欄位如下：

- `Backlog`：尚未排進本週工作。
- `Ready`：目標、負責人與驗收條件已明確。
- `In progress`：目前有人處理；一項任務只指定一位主要負責人。
- `Review`：已開 PR，等 A 或指定成員 Review。
- `Done`：PR 合併且驗收條件完成。
- `Blocked`：等待資料、規格或其他模組；Issue 要寫清楚阻塞內容和需要誰協助。

每張 Issue 寫清楚：**使用者／問題、任務目的、交付物、驗收條件、負責人、截止日、依賴**。工作跨 1–2 天以上就開獨立 Issue；小任務可放在所屬 Issue 的 checklist。

## 分支、PR 與 Review

1. `main` 保持可展示；不要直接推送到 `main`。
2. 一張 Issue 對應一個分支，例如 `feat/p-02-personal-feed`。
3. 表格中的 `P-01` 等是建立 Issue 前的暫用代號；建立 GitHub Issue 後，以 GitHub 指派的數字編號為準。PR 標題含該數字編號，描述用 `Closes #<數字>` 連回 Issue。
4. PR 至少附上：改動摘要、畫面截圖或 Demo 步驟、驗收結果、資料來源、已知限制。
5. 主要負責成員之外至少一人 Review；跨模組 PR 由 A 確認整合介面。
6. 合併後由負責人把 Project 狀態改為 `Done`，並在 Issue 註明驗收結果。
7. API 金鑰、LINE channel secret/token、個人資料或測試帳號密碼不得提交到 GitHub；使用本機環境設定並提交不含秘密的 `.env.example`。

## 每日非同步同步

每位成員在自己負責的 Issue 留三行短更新：

```text
昨天完成：
今天要完成：
卡住／需要誰協助：
```

遇到阻塞直接標記 `Blocked` 並@相關負責角色；不需要等到會議才提出。每次短會只處理看板上卡住的工作、跨模組依賴和下一個可展示版本。
