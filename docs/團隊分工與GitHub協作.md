# 團隊分工與 GitHub 協作

> 團隊以 A–E 作為成員代號，A 是你。所有分工都以工作內容稱呼，不使用隊長等職稱。GitHub Issues 是待辦與進度的主要位置；成員帳號尚未對應前，請在負責的 Issue 留言認領。

## 這一輪要完成什麼

先做出一條可展示的完整流程：**選擇關注 → 看見個人化法訊 → 核對立法院／法規來源 → 詢問並看引用 → 收到符合偏好的 LINE 更新**。原型目前是介面 Demo；各模組要逐步接上同一份核對資料。正式提交期限依專案簡章，內部目標是提前一天完成可提交版本。

## 共用資料格式

跨模組先使用同一份 `NewsItem`，欄位若要更動，由 A 開 Issue 記錄，再通知 B、C、D 一起確認。

```json
{
  "id": "demo-001",
  "title": "示意法訊標題",
  "summary": "淺白摘要",
  "topicTags": ["租屋權益"],
  "audienceTags": ["租屋族"],
  "status": "審議中",
  "publishedAt": "2026-11-12T08:00:00+08:00",
  "updatedAt": "2026-11-12T09:00:00+08:00",
  "sourceName": "官方資料來源",
  "sourceUrl": "https://example.gov.tw/",
  "meetingDate": null,
  "notificationLevel": "重要更新"
}
```

上面是格式示意；`example.gov.tw` 不是正式來源，請勿當成真實資料。`status` 至少要區分提案、審議中、通過、公布與施行；未知欄位留空並註明原因，不自行補猜。

## 先後順序與本週開始事項

1. **A：** 在 #1 定稿第一版情境與資料欄位，標出尚待決策項目；確認後通知 B、C、D 開始。
2. **B：** 先讀原型及 #1 欄位，提出排序規則；用至少 6 筆示例資料完成推薦 feed，不等完整後端才開始。
3. **C：** 先選定立法院與法規官方來源，建立 6 筆核對資料，再用同一批資料準備問答與拒答題。
4. **D：** 先完成帳號連結／通知流程和通知事件格式；可先用核對資料做模擬，不等待 LINE 憑證。
5. **E：** 先和 C 一起複核來源與狀態，再從 B、C、D 的首個切片開始寫手動驗收步驟。
6. **A + B + C + D：** 先以 JSON／靜態 fixture 接起一條端到端流程，再決定是否增加即時 API 整合。

## 任務狀態與協作規則

- 因目前還沒有 A–E 對應的 GitHub 帳號，Issues 暫不指派帳號。每位成員先在自己的 Issue 留言認領：`我負責，預計交付日期：____；目前需要：____`。確認帳號後再設定 assignee。
- 每項工作開獨立分支，例如 `feat/p-02-personal-feed`；PR 標題帶 Issue 編號，內文用 `Closes #數字`。
- `main` 保持可展示；不要直接推送到 `main`。PR 附上摘要、驗收步驟、資料來源與已知限制；涉及畫面時附截圖。
- 主責以外至少一人 Review；跨模組介面由 A 確認。API 金鑰、LINE token／secret 與個人資料不得放進 GitHub。
- LINE 真實推播只用經團隊確認的測試帳號；沒有安全測試條件時以畫面／本機模擬完成展示。

每天在負責的 Issue 留三行：

```text
昨天完成：
今天要完成：
卡住／需要誰協助：
```

卡住就直接在 Issue 說明阻塞點與需要的協助，不必等會議。Issue 有變更時同步通知依賴它的成員。
